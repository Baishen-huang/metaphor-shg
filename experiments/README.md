# 多方向并行实验与演化协议

本目录记录以 **git worktree + 独立分支** 隔离的并行实验，以及代际演化规则。

## 为什么需要隔离

项目的历史实验都在单一工作树里串行推进，导致两个问题：

1. **结论无法归因**。多个改动混在同一份代码上，某指标变化无法定位到具体改动。
2. **失败方向无法保留**。被否定的假设往往在后续重构中被覆盖，负面结果丢失。

worktree 隔离后，每个方向有独立的代码、独立的提交历史、独立的结果目录，可并行
推进且互不污染。

## 数据共享（关键）

语料与缓存体积大（`data/` 52MB）且许可受限，不复制。每个 worktree 通过
**目录联接（junction）** 指向主仓的 `data/`：

```bash
git worktree add -b exp/<name> .wt/<name>
powershell -NoProfile -Command "New-Item -ItemType Junction -Path '<abs>\.wt\<name>\data' -Target '<abs>\data'"
```

已验证：离线评测**只读** `data/`，不写回（`evaluate_hgnn` 前后 mtime 无变化）。
因此多方向并行读取是安全的。**唯一约束：不得在 worktree 内写 `data/`。**
新结果一律写到各 worktree 的 `experiments/` 下。

第一代的目标是**独立检验四条已有线索**，其中两条来自与本项目架构相似但基质不同

|---|---|---|---|

| `exp/source` | 特征口径一致性 | `type` 特征口径差是否污染 §6.2 的 +4.5pp？ | ❌ 否（§6.2 未受污染） |

| 分支 | 方向 | 来源 |
|---|---|---|
| `exp/emergent` | 查询侧标量重设计 | `exp/cascade` 发现 `n_emergent` 带真实信号（AUC 0.836 vs Ω 的 0.654），而 Ω 的几何平均+ε 下界合成把它稀释了 |

### 方向来源说明

- `dynamics` 起于一个已验证的数学事实：现有 `_conv` 是**无源项扩散**，行和恰为
  1.0，迭代收敛到连通分量的平稳分布。实测 500 轮后分量内平均余弦 = 1.000000。
  **但该事实只在渐近意义成立，H4 实际工作在 layers=2（余弦仅 0.388），
  故不能解释 H4 数字——这是第一代最重要的自我纠错。**
- `source` 起于一处**已复现的代码不一致**。
- `omega` / `degrade` 起于与外部系统的对照：前者借鉴"查询侧可观测标量统一授权
  结构证据排序权限"，后者借鉴"降级来源给独立封顶可靠度通道而非丢弃候选"。
  **只借机制，不借基质**——外部系统的守恒传输/双尺度场依赖 Tag 间传输率与
  "实际承载流量"观测量，本项目没有该变量，不引入。
- `emergent` 起于 Ω 失败后的**正确下一步**：证据表明是"合成方式"稀释了信号，
  而非"查询侧标量"这个概念本身无效。

## 演化规则（代际推进）

每个方向返回后，按下列规则决定是否进入下一代：

1. **结论必须有精确数字**，且给出可复现命令。无数字的方向不进入下一代。
2. **负面结果同样是一等产出**。被证伪的假设写入 `实验结论汇总.md`，不删除分支。
3. **存活判据**：改动必须在不破坏既有单测的前提下，移动至少一个被上报指标，
   或推翻/条件化一个已有结论。仅"代码更优雅"不足以进入下一代。
4. **主控独立复核**：每个方向的结论由主控**重跑关键实验**验证，不采信自述。
   第一代据此发现了两处需要修正的推断（dynamics 的渐近性、source 的因果链）。
5. **交叉验证**：若两个方向的改动都触及同一函数，下一代必须在合并后的基线上重测。
6. **合并顺序**：先合并**修正已上报数字**的方向，再合并**新增机制**的方向，
   最后合并**改变数学性质**的方向，因为后者会改变前两者的基线。

## 已知环境坑

1. **venv_jieba 会被删除**（发生过两次）。重建方式见上文；项目 memory 亦记录过。
2. **worktree 的 data junction 可能创建失败**（git 已建同名目录）。
   处理：`rmdir .wt/<name>/data` 后重建 junction。
3. **`evaluate_real.py --use-llm` 无 API key 时会静默回落到 `LocalHeuristicBackend`**，
   它不实现 `discover_batch`/`batch_refine`，于是 `--llm-cache` 根本不被消费，
   产出**假性 P1 = 0.434**。正确做法是用 `PrecomputedBackend` 喂缓存重放
   （P1 = 0.092）。这是本项目最危险的静默陷阱，已由 `exp/degrade` 独立发现。
